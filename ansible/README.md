# Ansible

This directory contains the server-configuration layer for ShelfSense IT. The flow is Terraform provisioning the Ubuntu EC2 instance, `scripts/bootstrap_server.sh` reading Terraform outputs and generating inventory, and Ansible configuring the host into a single-node K3s server with Helm available locally on that host.

## Current responsibilities

- `common`: refreshes the APT cache, installs shared base packages, and sets the system timezone.
- `storage`: resolves the retained EBS volume by its Nitro by-id metadata, safely creates ext4 only on a signature-free new volume, and mounts it by UUID at `/srv/shelfsense/postgres`.
- `k3s`: installs K3s, waits for the Kubernetes API and node readiness, and prepares `kubectl` access for the `ubuntu` user.
- `helm`: installs the Helm CLI so the existing Helm chart can be used later to deploy ShelfSense.

K3s provides the Kubernetes runtime and uses `containerd`, so Docker Engine is not installed on the EC2 server. Docker Compose remains the local-development deployment method only. Container images are built separately, pushed to the registry, and later pulled by Kubernetes when workloads are deployed.

## Inventory

Run commands from the `ansible/` directory so the local `ansible.cfg` is loaded automatically.

`inventory/hosts.ini` is generated by `scripts/bootstrap_server.sh` from the current Terraform output and is intentionally ignored by Git. Keep `inventory/hosts.ini.example` placeholder-only.

The generated inventory also carries the persistent EBS volume ID from the sensitive runtime Terraform output. The ID is never committed. The requested EC2 attachment name is not treated as the Linux device path: Nitro exposes EBS volumes as NVMe devices, so the storage role resolves the exact volume through `/dev/disk/by-id` metadata.

The storage role fails instead of formatting when it sees partitions, an unsupported filesystem, conflicting signatures, a root-device relationship, an unexpected mount, or a conflicting fstab entry. Existing ext4 data is mounted without reformatting. A correct second run performs no storage changes.

First-time formatting is deliberately disabled by the committed `postgres_storage_allow_initial_format: false` default. When the exact volume-ID mapping is otherwise safe but signature-free, the role stops before formatting. The controlled first-run procedure is:

1. Verify outside Ansible that the reviewed attachment is the new empty persistent EBS volume and that no retained data is expected on it.
2. Run the site playbook once with the typed boolean extra variable `--extra-vars '{"postgres_storage_allow_initial_format": true}'`.
3. Return to the default (`false`) for every later run. An existing ext4 filesystem is reused without requiring the flag.

The authorization flag is never a substitute for the device checks: immediately before `mkfs.ext4`, the role resolves the exact Nitro by-id mapping again and repeats block-device, root-tree, partition, filesystem, signature, and mountpoint validation. Do not put real volume IDs or connection metadata in committed variables or documentation.

Project-wide variables live in `inventory/group_vars/all.yml`, including the deployment user, timezone, shared base package list, and pinned K3s and Helm versions:

- `k3s_version: v1.34.8+k3s1`
- `helm_version: v3.19.0`
- `helm_archive_checksums` for the pinned Linux `amd64` and `arm64` release archives

If K3s is already present at the pinned version, repeated runs skip installation. If a different K3s version is already installed, the role fails clearly instead of upgrading or downgrading. Helm is reinstalled only when absent or when another version is detected.

Do not commit real IP addresses, DNS names, private-key paths, passwords, tokens, or other secrets.

## Commands

Run all commands from the `ansible/` directory so the local `ansible.cfg` is loaded:

```bash
ansible production -m ping
ansible-playbook --syntax-check playbooks/site.yml
ansible-playbook --check playbooks/site.yml
ansible-playbook playbooks/site.yml
ansible production -m command -a "sudo /usr/local/bin/k3s kubectl get nodes -o wide"
ansible production -m command -a "/usr/local/bin/helm version --short"
```

Check mode is useful for basic validation, but installation tasks that depend on remote system state or downloaded artifacts are not fully meaningful in `--check`.

## Bootstrap Script

Use the bootstrap script from the repository root with a placeholder private key path:

```bash
./scripts/bootstrap_server.sh /path/to/private-key.pem
```

The script:

- reads the server IP from `terraform -chdir=infra/terraform output -raw ec2_public_ip`
- generates `ansible/inventory/hosts.ini`
- waits for SSH and verifies connectivity
- runs Ansible syntax check, ping, and the site playbook
- verifies K3s service state, K3s version, node readiness, and Helm version

Repeated runs are intended to be safe. The script does not run Terraform `init`, `plan`, `apply`, or `destroy`, and it does not deploy ShelfSense, monitoring, or CI/CD components.

Use placeholder private key paths in local configuration examples, for example:

```ini
ansible_ssh_private_key_file=/path/to/private-key.pem
```
